# 엔지니어링 결정 기록

README를 스캔하기 좋게 유지하려고 분리한 문서입니다. "왜 이렇게 만들었나"에 대한 답을 프로젝트를 진행하며 그때그때 적었습니다.

## 기술 선택

**왜 Java 21?** 로컬에 JDK 21이 이미 설치돼 있고, Spring Boot 3.3이 공식 지원하는 최신 LTS. JDK 17을 추가 설치해 두 버전을 관리할 이유가 없었습니다.

**왜 Redis로 레이트 리밋?** 레이트리밋은 여러 톰캣 스레드(향후엔 여러 서버 인스턴스)가 "같은 사용자의 남은 토큰 수"라는 하나의 값을 동시에 읽고 쓰는 전형적인 공유 상태 문제입니다. 애플리케이션 메모리(`ConcurrentHashMap`)에 두면 인스턴스를 2대 이상으로 늘리는 순간 사용자별 한도가 인스턴스 수만큼 쪼개집니다. Redis는 모든 인스턴스가 공유하는 단일 저장소이면서, Lua 스크립트를 단일 명령처럼 원자적으로 실행해 "읽기 → 계산 → 쓰기"를 한 번에 처리할 수 있어 레이스 컨디션까지 같이 해결됩니다.

**왜 토큰 버킷(고정 윈도우 대신)?** 고정 윈도우("1분마다 카운터 리셋")는 경계 부근에서 허용치를 2배까지 봐줄 수 있습니다. 창구가 00~59초일 때 59초에 10건, 다음 창구 00초에 다시 10건을 보내면 실제로는 2초 사이에 20건이 통과합니다("burst" 문제). 토큰 버킷은 리셋 시점 개념 없이 "초당 refillPerSec개씩 꾸준히 채워지는 그릇"으로 모델링하므로 경계 폭주가 생기지 않고, 여유 토큰(`capacity`)으로 짧은 버스트도 자연스럽게 흡수합니다.

**왜 키를 해시로 저장?** DB가 유출돼도 키 원문이 없습니다. 발급 응답에서 딱 1회만 원문을 노출합니다.

**왜 비밀번호는 bcrypt인데 API 키는 SHA-256?** 해싱은 입력 엔트로피와 검증 빈도로 결정합니다. 비밀번호는 저엔트로피(사람이 만듦)·저빈도라 느린 bcrypt로 무차별 대입을 방어하고, API 키는 256비트 랜덤(추측 불가)·매 요청 검증이라 빠른 SHA-256 + 결정적 해시로 유니크 인덱스 단건 조회가 가능합니다.

**왜 OpenAI 호환 API 형식?** 기존 도구/SDK가 base URL만 바꿔 그대로 사용 가능합니다. 프로바이더별 형식 차이는 어댑터(`AnthropicClient`)가 내부에서 흡수합니다.

**왜 RestClient 타임아웃이 필수인가?** 외부 LLM API가 응답을 안 주면 톰캣 스레드가 하나씩 물려 스레드 풀이 고갈되고 서버 전체가 마비됩니다. connect 3s / read 60s로 차단합니다.

**왜 application.yml을 local/prod로 분리?** 환경마다 달라야 하는 값(DB 접속, ddl-auto)이 한 파일에 있으면 "배포 전에 바꿔야지"라는 기억에 의존하게 됩니다. 프로파일로 분리하면 구조가 강제합니다 — 로컬은 편의 기본값 + `ddl-auto=update`, prod는 기본값 없는 환경변수(미설정 시 부팅 실패) + `ddl-auto=validate`(스키마는 사람이 검토한 DDL로만 변경).

**왜 정적 HTML + 바닐라 JS로 최소 대시보드를 만들었나?** Tollm은 백엔드 인프라라 UI가 필수는 아니지만, 발표·면접에서 링크 하나로 동작을 시연하려면 최소 진입점이 필요했습니다. React 같은 빌드 도구를 들이면 별도 정적 호스팅이나 빌드 스텝이 늘어 이 프로젝트의 학습 스코프(백엔드)를 벗어납니다. `static/`에 두면 Spring Boot가 같은 포트에서 그대로 서빙해 인프라 추가가 0입니다.

**레이트리밋 데모에서 배운 것: 순차 호출로는 429가 재현되지 않는다.** 토큰 버킷은 경과 시간만큼 계속 리필되므로, 요청을 하나씩 기다리며 보내면 지연 동안 토큰이 다시 채워져 버킷이 고갈되지 않습니다. `capacity=10`을 실제로 초과시키려면 `Promise.all`로 동시에 쏴야 합니다 — "레이트리밋이 막아야 할 상황"이 순차적 저빈도 요청이 아니라 짧은 시간의 동시 폭주라는 걸 다시 확인한 계기였습니다.

## 팀 기능 (Add-on)

**왜 팀 API 키를 "재설계"가 아니라 "추가"로 넣었나?** 개인 사용자 흐름(인증/키/쿼터/레이트리밋/캐시)은 이미 검증된 코드라 손대는 순간 회귀 위험이 생깁니다. `ApiKey`·`RequestLog`에 nullable `team` 컬럼만 추가하고(개인 키는 항상 null, 기존 로직 100% 무손상), `UsageQuota`·`RateLimitService`·`ResponseCacheService`의 검증된 패턴(원자적 bulk update, Redis Lua, SHA-256 캐시 키)을 팀 단위로 그대로 복제했습니다. `relay(userId, body)`는 내부적으로 `relay(userId, null, body)`를 호출할 뿐이라 기존 테스트가 한 줄도 안 바뀝니다.

**팀 캐시는 왜 사용자 캐시와 다르게 "공유"를 택했나?** 개인 캐시는 `userId`를 키에 포함해 크로스오버를 막는 게 원칙이지만, 팀은 애초에 여러 사람이 같은 자원을 공유하려고 만든 경계입니다. 팀원끼리 같은 질문을 반복하면 캐시를 공유해 비용을 아끼는 쪽이 팀의 목적에 맞습니다. `buildKeyForTeam`은 `team:{id}`로 네임스페이스만 분리해 개인 캐시와 절대 충돌하지 않습니다.

**초대 링크를 왜 1회용 토큰이 아니라 재사용 링크로 만들었나?** 링크 하나를 여러 팀원에게 공유하는 게 초대의 자연스러운 사용 방식입니다. 만료(7일) 전까지는 여러 번 눌러도 안전하도록(멱등) 이미 멤버면 에러 대신 조용히 통과시켰습니다 — 재시도가 실패로 보이면 사용자가 혼란스럽습니다.

**팀 키 사용량이 개인 집계에 새던 버그를 어떻게 잡았나?** `RequestLog.user`는 팀 키로 보낸 요청에서도 항상 "발급한 사람"으로 채워지므로, `aggregateByUser` 쿼리에 `l.team IS NULL` 조건이 없으면 팀에서 쓴 사용량까지 개인 합계에 섞입니다. 실제로 팀 기능을 써보다가 개인 사용량이 부풀어 있는 걸 보고 발견했습니다. 회귀 방지 테스트(`팀_키_사용량은_본인의_개인_집계에_섞이지_않는다`)를 먼저 추가해 버그를 재현시킨 뒤 조건을 고쳤습니다.

**왜 API 키 단위 사용량을 별도로 추가했나?** 같은 사람이 개인 키를 여러 개 발급받으면 기존엔 "그 사람"·"그 팀" 단위로만 합산돼 어느 키가 얼마나 썼는지 구분할 방법이 없었습니다. `RequestLog`에 nullable `apiKey` FK 하나만 추가하고(기존 `user`/`team` 집계 로직은 그대로 둔 채) 새 집계 쿼리(`aggregateByApiKey`)만 얹어 `GET /keys/{id}/usage`로 노출했습니다. 총합 뷰(`/usage/me`)와 세분화된 뷰는 서로 다른 질문에 답하므로 대체가 아니라 추가 관계입니다.

## 배포 전 재검수에서 잡아 고친 항목

**URL 인코딩으로 관리자 인증을 우회할 수 있던 문제.** 두 인증 필터(`JwtAuthFilter`/`ApiKeyAuthFilter`)가 `request.getRequestURI()`(퍼센트 인코딩 원문)로 보호 경로를 판정했는데, Spring MVC는 **디코딩된** 경로로 컨트롤러를 매핑합니다. `GET /%61dmin/usage`(`%61`='a')는 필터의 `/admin` 접두어 매칭을 피해 필터를 통째로 건너뛰면서 `AdminController`에는 그대로 라우팅돼, 토큰 없이 전체 사용량 조회·타 사용자 쿼터 조작이 가능했습니다. Spring이 매핑에 쓰는 것과 같은 `UrlPathHelper.getPathWithinApplication()`(디코딩·정규화)으로 판정을 바꿔 필터와 컨트롤러가 항상 같은 경로를 보게 했습니다. 실서버 curl로 `/%61dmin`이 401로 막히는 것을 확인했습니다.

**`stream:true`로 월 쿼터를 무제한 우회할 수 있던 문제.** 스트리밍 응답은 SSE 텍스트라 토큰 파서가 못 읽어 비용이 0으로 기록되고, 실제 프로바이더 비용은 발생했는데 쿼터에는 반영되지 않았습니다. 스트리밍은 지원 대상이 아니므로 외부 호출 전에 400으로 거부합니다.

**캐시 키를 요청 본문 전체로 정규화.** 예전엔 `content`를 `asText()`로만 읽어 OpenAI 표준 배열 형식의 서로 다른 질문이 같은 키로 충돌하거나(남의 답이 나감), `max_tokens`/`temperature`가 달라도 같은 캐시를 받는 오응답이 있었습니다. "조금이라도 다른 요청은 다른 키" 원칙으로 바꿔 잘못된 히트를 원천 차단했습니다.

**외부 LLM 호출을 커넥션 풀 있는 클라이언트로 교체.** 예전 `SimpleClientHttpRequestFactory`는 풀이 없어 동시 요청이 늘면 매번 TCP+TLS 핸드셰이크를 새로 했고, 블로킹 호출이 톰캣 스레드를 최대 60초씩 물어 프로바이더가 느려지면 로그인·대시보드까지 먹통이 됐습니다. `JdkClientHttpRequestFactory` + `/v1` 동시 호출 격벽(Semaphore 100)을 도입해, 초과분은 즉시 503으로 되돌리고(스레드를 붙잡지 않음) 프록시가 포화돼도 다른 요청은 살아있게 했습니다.

**키 조회·단가표 조회를 Caffeine 캐시로 감쌈.** 둘 다 준정적 데이터라 캐시 히트 경로조차 DB를 4번 왕복하던 걸 줄였습니다. 키 인증 캐시는 폐기 반영 지연을 최소화하려고 TTL 30초 + 폐기 시 `@CacheEvict`로 즉시 무효화(실서버에서 폐기 직후 401 확인). 키 조회 결과는 엔티티가 아니라 식별자만 담은 record(`ApiKeyPrincipal`)로 캐시해 세션 종료 후 지연 로딩 문제를 피했습니다.

**prod fail-fast 강화 + 헬스체크.** 프로바이더 키를 prod에서 기본값 없는 환경변수로 바꿔(누락 시 부팅 실패) "키 없이 떠서 모든 프록시가 401 나는 조용한 장애"를 막고, `spring-boot-starter-actuator`로 `/actuator/health`를 열어 배포·Nginx 헬스체크가 가능하게 했습니다.

**운영 배포 blocker — DDL이 저장소에 없었던 문제.** prod는 `ddl-auto=validate`라 스키마가 없으면 부팅이 실패하는데 저장소에 DDL이 없었습니다. 엔티티 메타데이터에서 MySQL DDL을 뽑아 [`db/schema.sql`](../db/schema.sql)로 커밋하고, 배포 절차에 "DDL 선적용 후 기동"을 명시했습니다.
